## 分组方案

> 默认：Lead 1 个 + 执行子智能体 1 个 + 验证子智能体 1 个。子智能体之间不能互相通信，所以分组越少、交接文件越少。

## 权限矩阵

| 角色 | 可以改什么 | 绝对不能做什么 |
|---|---|---|
| Lead | `docs/{{FEATURE}}/` 下的规划与状态文件、`state.json` 推进（只经 `advance`）、派单与裁决 | 改业务代码；代替执行子智能体提交成果；代替验证子智能体宣告通过；代用户写验收结论 |
| 方案规划师（可选） | `DESIGN.md` 与 `planning/SOURCE-PLAN.md` | 改代码；在用户确认前写 `状态：已确认`；改其它 planning 文档 |
| 执行子智能体 | 只改 `EXECUTION-WORKPLAN` 各任务「产出文件」列出的文件，以及 `docs/{{FEATURE}}/evidence/` 下 `P*` 自测证据 | 装环境、重启进程、改 `state.json`、改已冻结的候选、写 `RELEASE-REPORT.md`、写 `handoffs/` |
| 验证子智能体 | 从冻结包安装到目标路径；只改 `docs/{{FEATURE}}/evidence/` 下 `V*` 核验记录与 `releases/<C>/RELEASE-REPORT.md` | 改业务代码与测试；顺手修 bug；为了通过而放宽判定标准；读 `-dev` 副本 |
| 督察使（可选，只读） | 只写 `docs/{{FEATURE}}/evidence/inspector-<日期>.md` | 改任何代码/台账/状态；回退越界（只报告不回退） |
| 用户 | 决定需求范围、验收标准、是否上线；回执 `ACCEPTANCE.md` 结论 | —— |

**互斥原则**：执行与验证在「改代码」和「装环境」上必须互斥。三权合一（改代码 + 部署 + 自我验证）时出问题无法定位，也无法自证清白。

## 派单与写范围

| 事项 | 规则 |
|---|---|
| 派单方式 | Lead 调 `subagent(prompt, description, name, cwd)`；`prompt` 必须写明读哪份计划、任务编号、产出文件、不做清单 |
| 任务板 | 多条任务用 `team_task_create`，`blocked_by` 表达先后，`write_scopes` 声明预期写范围 |
| `write_scopes` 的性质 | **只是建议性写范围**，PowerShell 可以绕过；真正的边界是「不做清单」+ 越界处理 |
| 子智能体间通信 | 不允许。交接只走磁盘文件 + 任务板 |
| 完成通知 | 子智能体结束会自动通知 Lead，Lead 不需轮询 |

## 候选与证据编号

| 项 | 规则 |
|---|---|
| 候选编号 | `C001`、`C002`… 全局递增，不复用 |
| 候选目录 | `docs/{{FEATURE}}/releases/{{CANDIDATE}}/`（含 `manifest.json`、`RELEASE-REPORT.md`、`files/`） |
| 证据目录 | `docs/{{FEATURE}}/evidence/{{CANDIDATE}}/`（执行线程 `P*`，验证线程 `V*`） |
| 冻结之后 | 不可修改；发现问题出新候选，不就地改 |
| 结论继承 | 可引用旧候选未受影响的结论，但必须在 `manifest.json` 的 `checks.reused[]` 写明 `check_id`、`from_candidate` 与 `reason` |

## 证据分级

| 级别 | 内容 | 用途 |
|---|---|---|
| A | 命令原文 + 退出码 | 最强，能复现 |
| B | 文件哈希 + 清单 | 证明产物身份 |
| C | 截图 / 页面回执 | 证明用户可见结果 |
| D | 自述 | 不计入通过，只作线索 |

规则：任何「通过」都要落到 A/B/C；只有 D 的检查项一律写成「未验证」。

## 越界处理

| 程度 | 情形 | 处理 |
|---|---|---|
| 1 | 改了范围内但未列出的相邻文件 | 记入「发现未处理」，补齐白名单，不干预 |
| 2 | 明确越界（改了不相关模块或做了别人的事） | 立即停止，回退该文件，Lead 记录并补授权 |
| 3 | 同一角色反复越界 | Lead 收窄该任务的 `write_scopes`、拆小任务、不再复用该角色上下文 |

## 变更与冲突

| 情形 | 处理 | 谁裁决 |
|---|---|---|
| 方案内已授权的细节 | 直接继续，不改文档 | Lead |
| 影响验收标准 | 改本文件 + `VALIDATION-WORKPLAN.md`，通知两个子智能体 | Lead 请用户确认 |
| 扩大范围（新功能 / 新账号 / 新环境） | 暂停该项，其余独立任务继续 | 用户 |
| 推翻方案前提 | 冻结执行，退回 `DESIGN` 重写 | Lead |
| 执行与验证结论冲突 | 以可复现证据为准，双方各交证据 | Lead |

## 完成定义

| 状态 | 含义 | 允许的声明 |
|---|---|---|
| `EXECUTING` 结束 | 代码写完 + 候选冻结 | 已开发完成 |
| `VERIFYING` 结束 | 证据齐备 + 独立核验通过 | 已上线可试用 |
| `TRIAL` 结束 | 用户实际试用并补记待验项 | 完整业务验收通过 |
| `DONE` | 问题清零、状态文件归档 | 已交付 |

禁止的说法：「应该没问题了」「基本完成」「测试通过了」（未说明测了什么）「部署好了」（未说明实际加载版本）。

## 必填项清单

- [ ] 存在标题完全等于 `## 权限矩阵` 的小节
- [ ] 矩阵表头为「角色 / 可以改什么 / 绝对不能做什么」三列，Lead、执行、验证三行齐全
- [ ] 每个角色的「绝对不能做什么」非空，且执行与验证在改代码 / 装环境上互斥
- [ ] 派单规则里写明 `write_scopes` 只是建议性写范围
- [ ] 越界处理三个程度都有对应动作
- [ ] 全文没有残留的未替换占位符
