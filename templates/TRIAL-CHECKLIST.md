# 待用户试用清单（TRIAL-CHECKLIST 模板）

> **用途**：给进入 TRIAL 阶段的 feature 一份统一入口——把「要用户试用什么、怎么算通过、结论写在哪」一次写清，让下一个人照着填就能把 TRIAL 走完，而不是靠记忆。
> **何时用**：候选已 `freeze` + `seal`、验证线程复核通过、`state.json` 的 `phase` 已是 `TRIAL` 时（前置自检见 §一）。
> **怎么用**：整份复制到 `docs/<feature>/releases/<C>/RELEASE-REPORT.md` 的对应小节（保留 `## 待用户试用清单` 这行标题），或作为试用清单附在本 feature 的 docs 里；填空位统一用 `〈…〉` 角标，填完删掉角标。

## 待用户试用清单

> 下面这一行标题是 `dsh_flow.py` 用正则认的锚点（`RE_TRIAL_CHECKLIST`，`tools/dsh_flow.py:60-63`）：允许带序号（如 `## 三、待用户试用清单`），但必须是**独占一行的标题**，正文里顺口提到这几个字不算。

### 一、前置检查

四项全 ✓ 才开始试用；任一项 ✗ 就退回上一步，不要让用户对着半成品试用。

| # | 判据 | 命令 / 检查方式 |
|---|---|---|
| 1 | 封存完成：`verification.json` 存在，且候选校验退出码 0 | `& $PY "<项目根>\tools\dsh_flow.py" verify -p "<项目根>" -f <feature> --id 〈C〉` → 退出码 0；同时 `Test-Path "<项目根>\docs\<feature>\releases\〈C〉\verification.json"` = `True`（对应 `dsh_flow.py:465-484`） |
| 2 | 异地快照已生成（封存件在项目外还有一份副本） | `Get-ChildItem "$HOME\.dsh\flow-snapshots\<项目名>\<feature>" -Filter "〈C〉-*"` → 至少 1 个目录，形如 `C001-20261122-131500`（快照根见 `dsh_flow.py:118`，形状见 `:3962`） |
| 3 | 发布报告已含试用清单标题 | `Select-String -Path "<项目根>\docs\<feature>\releases\〈C〉\RELEASE-REPORT.md" -Pattern '^\#{1,6}\s*[一二三四五六七八九十0-9、]*\s*待用户试用清单'` → 命中 ≥1 行 |
| 4 | 阶段已到 TRIAL | `& $PY "<项目根>\tools\dsh_flow.py" status -p "<项目根>" -f <feature>` → 输出含 `phase   : TRIAL`；若仍显示 `VERIFYING`，说明 Lead 还没 `advance --to TRIAL` |

### 二、试用项表

每条都要用户真的能动手做完，并给出可判定的结果。

| 编号 | 做什么（≤5 分钟） | 期望结果 | 观察重点 | 用户结论 |
|---|---|---|---|---|
| T1 | 〈打开 `releases/〈C〉/RELEASE-REPORT.md` 的试用清单小节，按 §一 逐条核对前置项〉 | 〈四条前置全部 ✓，命令输出与报告写的一致〉 | 〈前置项是否真的跑过（有命令原文），而不是只有「已完成」四个字〉 | 〈通过 / 不通过 / 待用户试用〉 |
| T2 | 〈按报告里的复现步骤做一次主链路操作，例如打开面板/调用命令〉 | 〈界面上出现 〈某个可见物〉，或命令输出含 〈某个字段=某个值〉〉 | 〈是否出现报错、是否静默失败、失败回执是否带上下文（HTTP 状态码 + 路径 + 错误码）〉 | 〈通过 / 不通过 / 待用户试用〉 |
| T3 | 〈断电/断连/重复点击一类异常路径：重复执行一次上一步〉 | 〈第二次操作被明确拒绝或幂等返回，不产生重复数据〉 | 〈是否有残留脏数据、是否需要手工清理〉 | 〈通过 / 不通过 / 待用户试用〉 |

编写规则（三条，缺一条这张表就没用）：

1. **每条必须能在 5 分钟内做完**——写不进 5 分钟的，拆成两条或降级为「上线后观察项」，不要塞进试用表。
2. **「期望结果」必须可判定**：写具体数值、可见物、或命令输出的关键片段（如 `total=3`、面板出现「健康」绿标），不写形容词。
3. **不许写「看看是否正常」这类无法判定的条目**——用户没法据此给结论，最后只能由 Lead 代填，那就等于没有试用。

### 三、结论怎么写

两个文件、两行结论，取值范围是封闭集合，且都必须**独占一行**（前后不加粗、不加标点）。占位符要全部填实，报告里残留未替换的占位符会让门禁直接判失败。

**A. `releases/〈C〉/RELEASE-REPORT.md`**——只允许三态之一（`THREE_STATES`，`dsh_flow.py:98`；判据 `check_report`，`:304-318`，结论行正则 `:315`）：

```text
结论：待用户试用
```

- 三态取值：`已上线可试用`（装上了、能跑，未做业务验收）｜`待用户试用`（等用户回执，默认停在这里）｜`完整业务验收通过`（用户试用过并说通过）。
- TRIAL 阶段的正常状态是 `结论：待用户试用`；只有用户试用后给了「通过」，Lead 才改写成第三态。

**B. `docs/<feature>/ACCEPTANCE.md`**——只允许三态之一（判据 `check_acceptance`，`dsh_flow.py:321-326`）：

```text
用户结论：〈通过 / 不通过 / 待用户试用〉
```

- **用户结论只由用户说，Lead 不得代填**：`通过` 是门禁放行 TRIAL→DONE 的唯一取值，代填等于伪造验收结论（门禁逐条检查这一行，且要求全文无未替换占位符）。
- 用户说「不通过」要走返工：由 Lead 决定回 `EXECUTING` 出新候选，不在此文件里就地改历史结论。

**C. 判据对照**（改模板或改门禁时按此表复核，别凭记忆）：

| 本模板小节 | 对应判据 | 位置 |
|---|---|---|
| §一 前置检查 第 1、4 项 | `check_seal` / 阶段状态 | `tools/dsh_flow.py:465-484`、`status` |
| `## 待用户试用清单` 标题 | `RE_TRIAL_CHECKLIST` | `tools/dsh_flow.py:60-63` |
| §三 A 三态 `结论：` | `check_report` | `tools/dsh_flow.py:304-318`（正则 `:315`） |
| §三 B `用户结论：` | `check_acceptance` | `tools/dsh_flow.py:321-326` |
| 三态取值集合 | `THREE_STATES` | `tools/dsh_flow.py:98` |

### 四、回填与留痕

1. **`ACCEPTANCE.md` §二 试用记录表**：一行一次试用，写清日期 / 项目（做了什么）/ 用户反馈原话（不加工）/ 处理（修了什么或记为什么不做）。
2. **`ACCEPTANCE.md` §七 变更记录**：追加一行，写「本次试用结论 + 对应的候选号」。
3. **台账**：用户口头/书面给了通过之后，由 Lead 执行

   ```text
   & $PY "<项目根>\tools\dsh_flow.py" advance -p "<项目根>" -f <feature> --to DONE --actor user
   ```

   `--actor user` 必须写 `user`——台账要能看出来「放行结论来自用户」，不是来自流程里某个角色。
4. 试用期间**不要改已封存的 `releases/〈C〉/` 里任何文件**：封存后任何改动或新增证据都会被 `verify` 判失败；要改就出新候选 `〈C+1〉`。

### 五、三条常见误用

1. **把本模板当成品**：模板里的 `〈…〉` 是填空位，直接整份复制到 `RELEASE-REPORT.md` 又不填，等于交了一份「还不知道要试用什么」的报告——门禁会因残留占位符或缺失结论行判失败。
2. **没证据就填「通过」**：`用户结论：通过` 只能来自用户真的动手试过；没有 §二 的观察记录、没有 §一 的命令输出，填「通过」就是伪造验收结论（第五不变量：无证据不算通过）。
3. **并发期冻结**：工作区里还有别人在写（`tools/`、`templates/` 共用）时不要 `freeze`/`seal`——冻结包会把别人的在途改动一起收进去，之后谁也说不清「装的是哪一版」。等「静止 ≥10 分钟」的窗口再做，并在 `manifest.note` 里写明冻结时刻工作区是否含他人在途改动。
